# 维护验证 skill

在 Codex 上，执行本 skill 前先阅读[平台映射](../poteto-mode/references/codex-tools.md)，包括其中针对各 skill 的说明。

在 GitHub Copilot 上，执行本 skill 前先阅读[平台映射](../poteto-mode/references/copilot-tools.md)，包括其中针对各 skill 的说明。

应用一变，功能地图就开始腐烂。本 skill 是对 `/create-verification-skill` 生成的 skill（或任何带功能地图的项目本地验证 skill）的保养循环。严格的单位是功能，而不是每句话：从源码覆盖每个功能文件，实测每个功能，而不把每一条 bullet 都终端化。

## 结果

选择其一，并说明是哪个：

- **clean** —— 每个功能都有源码覆盖和实测覆盖；没有值得交付的东西。不开分支，不开 PR。
- **changed** —— 产出一个 PR，包含已证实的文档、harness 或地图修正。
- **blocked** —— 覆盖未能完成，或已证实的修正无法安全交付。准确说明阻塞它的是什么。

## 修改范围

只修改验证 skill 自己的目录（它的 SKILL.md、features/ 以及它拥有的 harness 脚本）。运行期间绝不修改产品代码：地图描述的某个行为应用已经不再有，要么是文档漂移（修地图），要么是产品回归（报告它，不要在文档里掩盖）。

## 轮次

0. **定位目标。** 找到要维护的验证 skill：正文带有启动/驱动章节和功能地图的项目本地 skill（`.claude/skills/verify/`，或旧版生成器生成的 `.claude/skills/verify-*/`）。有多个候选 → 询问是哪个；一个都没有 → 停下来并指向 `/create-verification-skill`，而不是凭空造一个目标。

1. **索引卫生。** 读功能地图的 README，glob 其同级文件。修复缺失、多余、重复或失效的条目。轻量操作；不生成清单。

2. **源码波次。** 每个功能文件一个只读 subagent，并发启动。每个 subagent 从源码解释"这个面向用户的功能是如何工作的"，带引用地标出可能的文档漂移，并返回一份简洁的实测验证配方。子级绝不驱动应用，也绝不修改文件。返回结构：功能摘要 / 源码入口 / 可能的漂移或无 / 一份配方。

3. **对账。** 每个功能文件都有一份返回的摘要。把相互重叠的配方合并成尽可能少的应用状态。抽查被引用的漂移；不要重复证明已经干净的说法。梳理近期的改动，找出地图上缺失的面向用户界面——判定某个界面缺失之前，必须先有具体的源码路径。

4. **实测轮次。** 即使源码看起来干净也必须执行。coordinator 负责全部驱动操作；遵循该验证 skill 自己的启动模型——服务器和 UI 用一个长驻实例串行驱动，短命 CLI 则每次驱动用一个新的隔离会话（由该 skill 的 Launch 章节决定，不由本 skill 决定）。每个功能至少实测一次，并且无论出现什么故障，整轮都要守住三条不变量：(1) 绝不驱动一个自它上次做出意外行为以来未曾健康检查过的实例——首次驱动前先 doctor，以会话为单位时每个新会话都 doctor，任何一次驱动失败后再次 doctor，而当 doctor 看不出故障所在时（健康进程上的卡死 UI 状态），重置到已知状态或重新启动，而不是碰运气；(2) 到此为止采集的证据要挺过每一次清理，并在其指定位置实际核验，而不是想当然；(3) 一次驱动启动的任何东西都不得比该驱动本身活得更久——无论会话是卡住、退出还是共享，失败迭代的残留都要清理（共享实例时清理残留，而不是清理实例）。由 skill 漂移导致的 doctor 失败本身就是漂移：在修改范围内修好并重试一次——重启被该修复作废的东西，仅此而已——之后才把本轮标为 `blocked`。一个无法触达的功能，只有在写明具体前置条件（auth、entitlement、OS、外部状态）和已尝试的路径时才是 `verified-unreachable`；如果地图漏掉了该前置条件，那也是漂移。来自 triage 的任何 harness 修复，交付之前都要重新实测一遍。最终清理发生在本次运行最后一次驱动之后——包括那些重新验证——这样任何东西都不会比运行本身活得更久（证据保留，遵循该 skill 的规定）。

5. **分诊。** 错误或缺失的用户视角描述 → 文档漂移，修掉。harness 驱动不了的实际可用行为 → harness 缺口，修掉；harness 修复遵循与生成时相同的 helpers 规则（脚本可执行，调用方式写进 skill 正文）。应用行为真的坏了 → 产品缺口；为用户记录下来，不要放进本 PR。

6. **交付或停止。** 结果为 changed：产出一个只含已证实修正的 PR，先重读每个改过的文件。结果为 clean 或 blocked：不出 PR，如实报告结果与覆盖情况。

把简明的运行笔记（覆盖的功能、不可触达的前置条件、确认的漂移、结果）放在临时位置；不要提交它们。
