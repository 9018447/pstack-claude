# Notes 验证映射

本目录是验证 Notes 用户可见行为的持续维护之源。驱动应用之前先读本索引，再用对应的功能文件作为操作配方。

## 基线前提条件

- 用一次性数据目录在 `http://127.0.0.1:4173` 启动 Notes。
- 设置 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`，让并发运行不共享状态。
- 预置标题为 `Quarterly plan` 和 `Grocery list` 的笔记。
- 把 `control-notes` 和 `notes` CLI 加入 `PATH`。
- 运行 `control-notes doctor`，并要求得到预期的 URL、数据目录和构建修订号。
- 绝不驱动不是由本次验证运行启动的实例。

## 驱动约定

- 除非配方的前提条件另有说明，每个配方都从基线状态开始。
- 优先使用 ARIA 角色和无障碍名称，而不是 CSS 选择器或 DOM 位置。
- 把每条命令都当作字面内容对待。引号中的名称和标志保持原样。
- 浏览器操作通过 `control-notes browser` 执行。
- 终端操作通过 `control-notes cli -- <command>` 执行。
- 发生变更后恢复预置数据。清理时不要移除证明产物。

## 证明与跳过项的报告

- 采集用户操作和操作后的状态，而不只是最终画面。
- UI 证明包括一份 ARIA 快照和一张能看到应用标识的截图。
- CLI 证明包括命令、stdout、stderr 和退出码。
- 变更证明包括对所存值的第二个只读视图。
- 每个产物都要记录所用功能的 ID 和入口。
- 报告无法到达的路径时，附上尝试过的命令和未满足的前提条件。
- 不要把跳过的入口点报告为已通过其他路径验证。

## 功能条目契约

每个功能文件以一个 H1 标题和一段描述用户可见行为的段落开始。随后严格按此顺序使用四个 H2 小节。

1. `Sub-features` 列出简短 ID，每个行为一行。
2. `How to get to it (user POV)` 列出每一个用户入口。
3. `Driving it with <harness>` 以 `Preconditions:` 开头，使用带标签的列表项，把每个用户操作与确切命令和可观察结果配对。
4. `Gotchas` 列出可能浪费或作废一次验证运行的陷阱。

不要把实现细节写进映射。只写用户路径、稳定句柄、所需状态、命令和可观察的证明。

## 功能

- [创建笔记](./create-note.md) 覆盖浏览器和 CLI 创建、取消、持久化和清理。
- [搜索笔记](./search.md) 覆盖工具栏、键盘和 CLI 搜索，包括匹配、空结果和清除状态。
