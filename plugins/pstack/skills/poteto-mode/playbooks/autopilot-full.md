### 全量自动驾驶（Autopilot-full）

通过 [poteto-mode 的 Non-negotiables](../SKILL.md#non-negotiables) 解析 driver skill。

**你负责的是判定，绝不是 PR。一名 owner 把每个 PR 从构建一路带到 merge-ready，而任何东西要合并，都必须同时有你的干净 swarm 判定和操作员的显式合并点击。** 适用于"把这条队列交给自动驾驶""全量自动驾驶"以及一 PR 一 owner 的程序。Orchestrate 运行的是一个常设程序，其协调者自己落地已验证的工作，worker 绝不合并。而在这里，每个 PR 的 owner 承担直到 merge-ready 的完整生命周期，操作员点击合并，root 只保留验证、会签和审计。

1. **标记操作员点名的条目，并遵守 state-then-wait。** 操作员点名的条目留在操作员手里。操作员负责审查和点击，任何 owner 都不得代为合并。操作员要求陈述协议或计划时，给出陈述即止。执行只在操作员显式 go 之后开始。听到 go，就把完整的程序目标写进常设指令，并在你的 todolist 里复述。该目标跨回合有效，直到队列做完。第一名 owner 启动之前，把程序规模告诉操作员：owner 数量、第一轮的 verifier lane，以及第 4 步的每 PR 两次 fix-forward 上限。owner 超过三名的程序要等操作员对这个规模的 go，除非操作员的请求已经点明了规模。
2. **为每个 PR 派生一名 owner，承担完整生命周期并尽早留痕。** 为整个程序解析一次 forge。GitHub CLI（`gh`）是默认。如果 `command -v origin` 成功且 Origin 能解析出该仓库，PR 的创建、编辑、查看、watch 和合并操作都用 `origin pr ...`。否则继续用 `gh` 并记录这一回退。绝不强求 Graphite（`gt`）。每个 PR 一个后台 subagent，在它自己的工作树里，端到端负责：构建、第一次推送、一个 ready 的 PR、对真实产物做 self-proof（**prove-it-works** 原则 skill）、按 `../references/bugbot-triage.md` 以怀疑态度分诊 review-bot 意见、一次 slop-strip（**deslop** skill，`/deslop`）、`/no-comments`（**no-comments** skill）、rebase 到当前主干，以及跑到全绿的 babysit 循环（`playbooks/babysit.md`）。在大约 15 分钟内，每个 owner 都按 **show-me-your-work** skill 启动一条 `decisions.tsv` 轨迹，推送第一个分支快照，并以 ready、绝非 draft 开好 PR。此后，owner 每完成一个可验证单元就再推一次自己的分支（开着 hooks，WIP 提交也可以）。在 self-proof 之前就开 PR，让 URL、决策和检查构成持久轨迹。让 `decisions.tsv` 保持未提交，随报告一并返回。subagent 一启动，owner 就把它的 ID、预期运行时长（至少按该类过去最长一次估）和状态记入一个以同样方式维护的 `children.tsv`。owner 在 code-ready 报告和 babysit 之前完成第一次 rebase，无论主干是否已漂移。修复轮中，owner 沿用那个合并基。owner 只在三种情况下再次 rebase：合并准备（第 5 步）、与主干出现 `git merge-tree` 冲突、或 CI 失败源自主干上的变更。交付的代码定稿、做完 slop-strip 和 `/no-comments` 后，它上报 code-ready head SHA。之后每次改变补丁的推送，也要上报其 SHA。self-proof、CI 与 babysit 从此与 swarm 并行推进。self-proof、CI 和 babysit 全部完成时，owner 带着该 head SHA 上报 merge-ready。在开启一轮验证的推送之前，先跑仓库的 CLAUDE.md 文件和规则为所涉路径点名的预审查检查。在已提交的 head 上跑。hook 通过不构成证明。每次发布 rebase，先做 `ls-remote` 检查，再用 `git push --force-with-lease` 推 owner 自己的分支。绝不 force-push 共享分支。owner 推进到 merge-ready 即停。任何 owner 都不执行合并。第 4 步把关判定，第 5 步把合并交给操作员。
3. **让 owner 真正并行，绝不叠栈。** PR 自包含时同时跑多个 owner：每分支一个写者、文件不相交、跨 PR 漂移交给 rebase 吸收。只有真正重叠的工作才串行。自包含的 PR 直接从 main 分出，有先后依赖的工作则先合并再开分支。一个例外：必须拆分真正依赖性变更的 owner，可以短暂持有一段私有的基础分支栈。
4. **每轮在合并之前都做 swarm 验证。** 一轮从 owner 的 code-ready head SHA 开始，此后每次改变 PR 补丁的推送也都开启新一轮。在该 SHA 上，按 **swarm** skill 扇出多个并行的独立 verifier，汇总为一个判定。合并需要来自该轮的干净判定，且该轮补丁与 merge-ready head 一致。判定之前先审计 merge-ready 报告里的凭证。各 lane 的任务：在该 SHA 上重跑门禁。通过 driver skill，在变更触及的真实表面上现场验证承重行为。审计 diff，不信任 PR 描述。审计以两条或更多审查 lane 执行，各配完整 brief。每条 lane 一个主焦点，例如与主干的消费方一致性、生命周期与竞态、或数据与配置安全。**对主干的回归 lane。** 在当前主干上跑同样的承重场景。主干没有该功能时，就记录这一事实，改为把关 diff 新增的行为加上用户等待的最终状态，而不是假装主干也能产出它。live lane 是下限，没有它的判定不算干净。没有 root 的干净判定就不合并。lane 返回后，先把每个被证实的发现归类，再向 owner 交付任何东西。lane 以 note 形式登记的缺陷也是发现。只有当 diff 是成因时，发现才阻塞合并——即 PR 让某个行为比主干上更糟，或 PR 声称的修复并不生效。把阻塞性发现打包成一次 fix-forward 发给 owner。主干上已有的缺陷不归这个 PR 修：开个 issue，或在 PR 描述里列为已声明的缺口，不要为此扣住合并。对每个阻塞性的行为发现，要求一条覆盖所有同类缺陷点的失败测试（红测）。测试无法呈现该缺陷时，改为要一份复现凭证。把该缺陷加进下一轮的审查 brief。**限定轮数。** 只有第一轮跑完整 swarm。后续轮只验证 fix-forward，别无其他：重跑门禁，在新 head 和主干上重跑暴露过每个阻塞发现的探测，再跑一条以 fix-forward diff 为范围的审查 lane。第一轮的 lane 结果按 `playbooks/shipping.md` 的 patch-id 规则保持有效。绝不允许因为 verifier 还能找到更多问题就开启新一轮。给每条审查 lane 的指令是：报告 diff 会破坏什么，而不是所涉文件里所有毛病；除非操作员要求，否则不做变异或 fuzz 攻势。每个 PR 至多两次 fix-forward。阻塞发现在第二次之后仍然存在，就停止该 PR 的工作，连同发现和证据上报为 blocked，由操作员选择再来一轮、拆成更窄的 PR，或关闭它。
5. **判定干净后 owner 交接，新的 owner 接手下一项。** merge-ready head 必须是刚 rebase 到主干上的。合并准备绝不早于一轮 lane 的启动，并且以交接前那一刻对当前主干的 rebase 收尾。合并准备的 rebase 之后，owner 上报新的 head SHA。交接之前 CI 必须在该 head 上通过，该轮判定是否仍然成立由 patch-id 规则决定。如果操作员合并之前主干又动了，重新验证由 `playbooks/shipping.md` 的 patch-id 规则管辖。新 head 使就绪状态失效。patch-id 未变时，只有在核查过它对新 base 和新上下文仍然适用之后，实质审查才可沿用。重跑检查和可合并性。owner 把已验证、merge-ready 的 PR 连同其 swarm 判定和固定的 SHA 呈给操作员，然后返回。新的 owner 按 poteto-mode 的 Subagents 章节从队列接手下一个自包含条目。操作员负责审查并以 squash 方式合并。任何 owner 都不亲手执行合并。每一项都等操作员的点击——正是操作员点名条目一直享有的那道门。root 的干净判定是这次点击的前提，绝不是它的替代品。
6. **运行 root 层。** 对已固定的门禁或预算值做出真正新的上调（CI 只允许收紧的那种限制）需要你新做出的会签，且只有在拿到 verifier 证明之后才给。操作员的授权或常设指令已覆盖批准事项时，该会签即为批准。owner 以该工具批准契约允许的形式记录它，并附指向 root 会签的指引。由一条 lane 拿该会签核对记录。root 绝不给出或绕过 forge 强制要求的批准。吸收已经落到 main 上的值属于漂移，不是上调。每小时对所有 owner 跑一次审计 tick。把每个 tick 配置成 dynamic 模式下一个真实的 `/loop`，让它自行安排唤醒，而不是阻塞在一个 sleep 上。绝不把节奏托付给记忆或有损的完成通知。每个 tick 都先从磁盘重读本 playbook（已安装插件下的 `skills/poteto-mode/playbooks/autopilot-full.md`），再重读常设目标，拿这两者审计当前运行，并在该 tick 内修复漂移。用通用的存活或状态探测去探每个 owner，并收集决策轨迹。只把副作用算作进展：提交、推送、PR 或检查的变化，以及存入 store 的报告。报错的 lane，或超过预期运行时长仍无副作用的 lane，一律视为卡死：立即让它停止并派出替补，不要等它体面地返回。tick 以第 2 步要求的已推送分支和决策轨迹来评判 owner，agent 无法开始一个回合的 owner 就地更换。每个 tick 还要对程序的 agent 名单（平台提供时）以及每个 owner 的 `children.tsv` 跑同样的卡死检测。无论停止操作是否生效，root 都要让 owner 把每个卡死的 subagent 记为 stuck，并且在其工作仍被需要时更换它。替补再卡住就走同样的步骤。owner 做不到时，这两步都由 root 来做。卡住本身既不证明工作完成，也不丢弃工作。合并成批发生时，跑一次复盘和一次合并后的机器人评论清扫。直到没有任何受托工作剩余，哪怕已过最后一次合并，tick 才结束。
7. **操作员叫停，立即全体停下。** 操作员的暂停或收队指令立即以零写入指令的形式到达每个 owner。owner 在操作员解除之前保持待命。

**回复：**队列，含每个 PR 的 owner、状态和 head SHA。每个判定以及产出它的 swarm。合并了什么，每个新 owner 接了什么。已给出的会签及原因。仍开放的、等待操作员的门禁。收集到的决策轨迹存放在何处。
